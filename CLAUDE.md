# hosty.live web app and canisters — guide for AI assistants

React 18 + Vite + TypeScript web app of hosty.live, plus the Motoko canisters (`canisters/src/{backend,auth,status-proxy}`) and hosty's build of the certified-assets frontend canister (`canisters/certified-assets`, see its README). The API lives in `../hosty-live-api`; read its CLAUDE.md for the system model (builder principal, deploy sessions, module store, production).

## Commands

- Typecheck: `npx tsc -b --pretty false` (the `build` script runs it before `vite build`). Lint: `npm run lint` (16 pre-existing errors across about ten files: unused vars, `{}` types in the generated `.did.d.ts` bindings, react-refresh exports; compare the count with main rather than expecting zero).
- Dev against a local API: `VITE_HOSTY_API_BASE=http://localhost:3999/api npx vite --port 5199`. Sign-in uses Internet Identity (`https://id.ai`); for automated UI checks seed the origin's IndexedDB `auth-client-db` / `ic-keyval` with `identity` (Ed25519 key JSON string) and `delegation` (delegation chain JSON from a test root key), plus `hosty_principal` / `hosty_access_token` in localStorage. Use a port of its own so a real local session is not overwritten.
- Motoko: `moc $(mops sources) --check canisters/src/backend/main.mo`; `tools/moc-check.sh <reference checkout>` also emits the Candid and checks stable compatibility; `tools/gen-backend-bindings.sh <did>` regenerates `src/api/backend/` (keep `../hosty-live-api/src/ic/backend.did.*` in sync, see the API's CLAUDE.md).

## Things that are not obvious from the code

- `src/api/certified-assets/sync.ts` is a verbatim copy of `../hosty-live-api/src/ic/certified-assets-sync.ts` (the sync protocol, `_redirects` and `_headers`). Edit the API copy, run its tests (`yarn test` there), then copy the file here.
- `src/api/management/management.did.*` is the IC management interface binding; `canister_settings` / `definite_canister_settings` carry `environment_variables` (added 2026-10-20), so every `canister_settings` literal needs `environment_variables: []` (opt none = unchanged). Management calls need `.withOptions({ effectiveCanisterId })`, otherwise the boundary node answers `canister_not_found` for `aaaaa-aa`.
- Two kinds of environment variables: the deploy dialog's **Build environment variables** are the process env of the server-side build only; **Canister environment variables** (`src/components/panel/CanisterEnvCard.tsx` on the canister page) are canister settings. The card reads `canister_status` and writes `update_settings` with the user's II identity (controllers only), read-modify-write, then calls `refresh_env` on certified-assets canisters so `PUBLIC_*` values appear in the `ic_env` cookie at once. Only `PUBLIC_*` names are published and their values are public; the legacy assets module never publishes them (the card says so and points to "Reset canister").
- `canisters/src/shared/management.mo` is shared with the blackholed status proxy. `DefiniteCanisterSettings` deliberately lacks `environment_variables`: the backend decodes the proxy's cached `canister_status` replies with it. `update_settings` takes `environment_variables : ?[EnvironmentVariable]` (`?[]` clears, `null` keeps).
- The backend canister clears a canister's environment variables when it leaves a renter (`setupSystemOwnership_`) and when it is rented (`setupUserOwnership_`); they survive the pool reinstall otherwise. Checked on a local replica (PocketIC time travel past the 24 h rental), including a negative control with the previous code.
- An empty canister (no module, e.g. imported without reset) cannot be granted deploy access or deployed to: both calls go to the assets module. The canister page shows "Install asset module" instead of Deploy (`useCanisters.installAssetModule`, `performInitialCanisterSetup` in install mode, controllers untouched), import without reset installs it when the canister is empty, and Settings' grant (`api/certified-assets/deploy-access.ts`) checks each canister with `canister_status` first and lists per-canister reasons (empty, non-asset, backend, out of cycles) instead of one generic error. Agents do the same through the API's `hosty_setup_frontend_canister`; keep `assetStorageHash` equal to the API's `HOSTY_ASSETS_MODULE_HASH`.
- Alias and description are registry metadata too. The web app sets them as the user with `updateCanister`; the API sets them for agents through `updateCanisterFor(user, cid, { alias; description })` (builder only, the user must be among the canister's `userIds`; `frontendUrl` is deliberately left out, custom domains stay with the web app). Both share `updateCanister_`, which traps instead of rejecting.
- Kind (frontend/backend) is registry metadata, switchable while the canister runs the asset module: the rent dialog (`CreateCanisterModal` with `rent`) offers Backend, the frontend card offers "Use as backend" and the backend card "Use as frontend" (`useCanisters.setCanisterKind`; the backend canister refuses frontend for any other module). Nothing is installed or wiped by the switch; the first Wasm install replaces the asset module (reinstall, confirmed in the dialog). The API marks a canister as a backend before an unattended install, because the backend canister's `installCode` serves kind backend only.
- When a rental returns to the pool (and when it is rented), the backend canister deletes its canister snapshots and clears its Wasm chunk store (`clearRentalLeftovers_`): both survive a reinstall, and a renter is a controller who could `load_canister_snapshot` the previous renter's state. Checked 2026-10-21 on a local icp network via `donateCanister` (same `preparePoolCanister_`), with main's code as negative control (snapshot and chunk survive there). A canister re-enters `canistersPool` only after that preparation (`returnToPool_`), so a rent cannot pick it up mid-cleanup.
- `?topup=1&amount=<TC>` on a canister page opens the top-up dialog prefilled: the API hands agents this link for low-cycles canisters. Card payments: CyclePay (`src/utils/cyclepay.ts`, direct links `cyclepay.org/c/<canister>/<usd>` and `/b/<principal>/<usd>`, whole dollars 5 to 100, no sign-in, 1 XDR per TC plus Stripe's fee; the top-up dialog prefills the dollars for the entered TC with `usdForTC`, keep its pricing equal to the API's `src/canisters/cyclepay.ts`) next to Cycle Express (`cycle.express/?to=<id>`, no amount) in the top-up dialog, the shared canister page and the Cycles page. Agents get the same links from the API, and tracked CyclePay orders through `hosty_create_cycles_order`. Agents with an approved deploy session can also create canisters and top them up from the user's cycles balance (API `hosty_create_canister`, `hosty_top_up_canister`); the session approval card says so and shows the balance.
- ICP deposits (Cycles page, "Deposit ICP", `DepositIcpModal` / `useIcpDeposit` / `src/api/icp`): the user sends ICP to their **own** ICP account (principal, or its account ID for exchanges) with a QR code or an ICRC-22 `icp:<principal>?amount=<ICP>` link (what the NNS dapp and Oisy scan), so no wallet has to set a memo; the web app then converts as the user: `icrc1_transfer` to the CMC subaccount of the user with the ICRC-1 memo "MINT" (8 bytes LE), then `notify_mint_cycles`, which credits the user's cycles-ledger account. Unnotified transfers are kept in localStorage and notified again (the notify is idempotent and only the user can claim their subaccount). Checked 2026-11-06 on a local icp network (account ID, memo, mint, repeat notify, foreign caller refused).
- Deploy session approval (`DeploySessionCard.tsx`, on every panel page): the card shows the request code the agent also shows, the principal of an agent-held key (`sessionKeyPrincipal` in `lib/delegation.ts`, computed from the DER key the delegation goes to, not taken from the API), the token name and creation date, the full request date and the agent's purpose; it warns when more than one agent request is pending and offers "Decline and revoke token" (the API's token revoke declines and ends that token's sessions). `ensureActiveSession` (canister page Wasm install) requests the web app's own session: since 2026-11-06 the API never answers it with an agent's pending request, which it used to approve silently. The API side is in its CLAUDE.md ("Approval flow").
- The Wasm install dialog (`DeployWasmModal.tsx`) can install from the module store: a module hash or the id of a canister whose module is stored (`GET /modules/canister/:id`), sent as `POST /deployments/deploy-module`.
- Freezing threshold: canisters hosty.live creates (`createCanisterOnLedger`, the API's `hosty_create_canister`) and resets get 30 days (`constants/canisterSettings.ts`, the API's `USER_CANISTER_FREEZING_THRESHOLD`, the backend pool's). Until 2026-10-23 creation used 365 days: the frozen reserve (idle burn x threshold) then exceeds a ~1T balance once the asset canister grows its memory on the first upload ("cannot grow memory"), and top-ups barely help. The grant (`deploy-access.ts`), web deploys (`useDeployments`, Wasm installs included) and the API's frontend setup lower a higher threshold to 30 days as the user. Backends need it as much: co6yk-kyaaa-aaaau-ahgea-cai (365 days, 102 MB heap) rejected calls with IC0532 "cannot grow memory" while holding ~2T, and lowering fixed it at once (a reset would have wiped its state). The API lowers it before every backend install, and agents have `hosty_lower_freezing_threshold`: with a deploy session as the user, on the unattended route through the backend canister's `lowerFreezingThreshold(user, cid)` (builder only, `unattendedTarget_` checks, never raises, invalidates the proxy cache itself; checked 2026-10-28 on a local icp network: 365 d lowered, 30 d and 7 d kept, frontend kind / other user / non-builder refused, cached status dropped). `lowerFreezingThreshold` and the reset call the status proxy's `invalidateCache` as the user. The deployed proxy refreshes entries older than 60 s on `loadState` (checked 2026-10-28), but `queryState` returns an entry of any age: readers must check its timestamp (`fetchCanisterStatus` does, the API now too).
- Cloud engine canisters (`network` on `Canister`, from the registry's `CanisterData.network`): free canisters on hosty's cloud engine subnet, created by the API (`POST /canisters/create` with `network: "cloud"`, `canistersApi.createCloudEngine`), whose **only controller is hosty's cloud engine key**. The web app therefore never signs anything on them: `useCanisterStatus(id, { network })` reads `GET /canisters/:id/status`, `CanisterEnvCard`, `BackendModuleCard` (logs, snapshots), `useCanisters.installAssetModule` / `deleteCanister` / `setCanisterKind` and the deploy hooks (no builder grant, no session for Wasm installs) take the API path when `network === 'cloud'`. The canister page hides cycles, top-up, withdraw, custom domain, ownership, controllers, reset and donate for them and treats the user as able to manage (`isController`). `CreateCanisterModal` offers Cloud engine (default while the quota of `GET /canisters/cloud-engine` allows) next to Mainnet. The status proxy cannot read engine canisters (its `canister_status` is unbounded-wait), hence the API route. Registry: `registerCloudEngineCanister` / `markCloudEngineCanisterDeleted` / `countCloudEngineCanisters` / `listCloudEngineCanisters` (builder only); `registerCanister`, `deleteCanister`, `donateCanister` and the unattended route refuse cloud engine entries. Migrations: the first marked every existing entry mainnet; the rename of 2026-11-02 rewrote the stored `#testnet` tag to `#cloud` (active `with migration` in `main.mo`, comment it out after the upgrade as with the earlier ones; stable compatibility checked with `tools/moc-check.sh`). Naming: the feature was called "testnet" until 2026-11-02; the project owner's name is **Cloud engine (free)** (free tier today, paid canisters on the engine are conceivable later), the UI says "Free-tier canisters have no fixed expiry or other limitation but may be deleted at the provider's discretion". Code uses `cloudEngine` / `CloudEngine`, the wire value is `cloud`; do not reintroduce "testnet". Engine behaviour: see the API's CLAUDE.md.
- Connected apps (MCP OAuth, H9; the API's `MCP_OAUTH_ENABLED`): `/oauth/consent?request=<id>` (`pages/oauth/OAuthConsentPage.tsx`, outside the panel layout, behind `ProtectedRoute`; sign-in returns with the query) shows who asks (verified host or "name not verified"), where the approval goes (redirect host, red warning for hosts outside `isKnownRedirectHost`), what the app gets and never gets, and Approve/Decline; it never approves by itself. Settings' `AgentAccessCard` shows "Connect Claude" and "Connected apps" (Disconnect = revoke the grant, which ends its deploy sessions) only when `GET /oauth/grants` answers (404 = flag off: the card stays the token-first layout); the token path then sits in a collapsed "For scripts and other MCP clients" section. `DeploySessionCard` says "Connected app … connected <date>" and offers "Decline and disconnect app" for `requestedByConnectedApp` sessions. `_headers` puts `frame-ancestors 'none'` on `/*`: an `/oauth/*` block would not reach the page, since the SPA rewrite serves `/index.html` with its own headers.
